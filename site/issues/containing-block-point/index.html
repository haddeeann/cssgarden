The Containing Block Is the Point

Every positioned element measures itself against a rectangle you never drew. Understand the containing block and the four position values — and their bugs — click into place.

Every positioned element in CSS measures itself against a rectangle you never drew. That rectangle — the containing block — is the real subject of CSS positioning. The four keyword values (relative, absolute, fixed, sticky) are just four different answers to one question: which box is the containing block, and what are its edges?

Most positioning tutorials introduce the four values as a flat list and leave the containing block as a footnote. That ordering is backwards. Once you understand the containing block, each value clicks into place on its own — and the bugs that have been confusing you for years suddenly have obvious explanations.

The invisible rectangle everything measures from

A "positioned element" is any element whose position is anything other than static, the default. When you write top: 20px or left: 50%, those values are not measured from the edge of the screen or the edge of the parent. They are measured from the edges of the containing block.

For position: static elements, there is no containing block in the positioning sense — the normal flow handles placement. For every other value, the browser locates a specific rectangle, and which rectangle it picks depends entirely on the position value you chose.

The complete map, in one place:

  • relative — the element's own box in the normal flow. Offsets nudge it visually, but it still occupies its original space.
  • absolute — the padding box of the nearest ancestor whose position is anything other than static. If no such ancestor exists, it falls back to the initial containing block, which is the viewport.
  • fixed — the initial containing block (the viewport), unless an ancestor has a CSS transform, filter, or will-change: transform applied, in which case that ancestor becomes the containing block instead.
  • sticky — the element's scroll container: the nearest ancestor that actually scrolls.

That last "unless" is where the bugs live.

What each value actually does

position: relative

The element stays in the normal flow. Its original space is preserved; sibling elements do not collapse into the gap. The top, right, bottom, and left properties shift the painted position relative to where it would have been.

.nudged {
  position: relative;
  top: 8px;
  left: 8px;
}

position: relative does two other things at the same time. It establishes a containing block for any absolutely-positioned descendants inside it. And if you also set z-index to anything other than auto, it creates a new stacking context — a quarantine zone for z-index values, covered below.

position: absolute

The element is removed from the normal flow entirely. Siblings close the gap as if it were never there. The element then positions itself against the padding box — not the border box, the padding box — of its nearest non-static ancestor.

.parent {
  position: relative; /* establishes the containing block */
}

.child {
  position: absolute;
  top: 0;
  right: 0;
}

The most common absolute-positioning bug: forgetting to add position: relative (or any non-static value) to the intended parent. Without it, the browser walks up the DOM looking for a positioned ancestor and may end up measuring from the viewport — or from a distant grandparent you didn't intend.

position: fixed

Fixed positioning is absolute positioning against the viewport. The element is removed from the flow, scrolls with nothing, and stays locked to the same screen position no matter how far the user scrolls. It's the right tool for persistent navigation bars and overlays.

.toolbar {
  position: fixed;
  top: 0;
  left: 0;
  width: 100%;
}

The failure mode is precise and consistent across every modern browser: if any ancestor of a fixed element has a CSS transform, filter, or will-change: transform applied, that ancestor becomes the containing block instead of the viewport. The element is no longer fixed to the screen — it is fixed to that transformed box. This is correct spec behavior, not a browser bug. The practical fix is to move fixed elements to the <body> level, outside any transformed ancestors.

position: sticky

Sticky is the hybrid. The element behaves like a relatively positioned element until it reaches a threshold within its scroll container, then it sticks in place like a fixed element — but only within the bounds of its parent. When the parent scrolls out of view, the sticky element goes with it.

.section-label {
  position: sticky;
  top: 16px; /* distance from the scroll container's edge where sticking begins */
}

Full support across evergreen browsers landed with Safari 16 in late 2022. The value is safe to use without a fallback for most audiences today.

Two bugs that make sense now

Armed with the containing block model, two of the most-reported CSS positioning bugs become immediately readable.

Sticky stops sticking: the overflow trap

A sticky element can only stick within its scroll container — the nearest ancestor that actually scrolls. When you set overflow: hidden on an ancestor, you silently promote that ancestor into a scroll container (one that never shows its scrollbar). The sticky element is now confined to a container that never scrolls, so it never reaches its threshold, and it never sticks.

/* Kills sticky on any descendant */
.wrapper {
  overflow: hidden;
}

/* Clips visually without creating a scroll container */
.wrapper {
  overflow-x: clip;
}

overflow: clip is the correct replacement when you want to hide overflowing content without accidentally creating a scroll container. It has full support across evergreen browsers and does not affect sticky descendants. overflow: hidden on a <body> element is the single most common cause of "my sticky header stopped working" reports.

z-index stops working: stacking contexts

A stacking context is a self-contained layer. Elements inside one stacking context cannot paint above elements in a sibling stacking context, regardless of their z-index value. The trigger: any positioned element (relative, absolute, fixed, or sticky) with a z-index value other than auto creates a new stacking context.

.card {
  position: relative;
  z-index: 1; /* creates a stacking context */
}

.modal {
  position: fixed;
  z-index: 9999; /* only wins within its own stacking context */
}

If .modal is a descendant of .card, its z-index: 9999 is evaluated only within .card's context. It cannot paint above a sibling of .card that has a higher z-index, no matter how large a number you write. The fix is structural: move the modal element to the top of the DOM, outside any stacking contexts you don't control — or use the popover attribute, which handles this automatically.

Sticky on table elements

One edge case worth knowing before you hit it: position: sticky does not work on elements with a display: table-* computed value, which includes <thead> and <tr>. Applying sticky to a <thead> has no effect. The working pattern is to apply it directly to the <th> or <td> cells inside the header row.

/* Does not work */
thead {
  position: sticky;
  top: 0;
}

/* Works */
thead th {
  position: sticky;
  top: 0;
}

The mental model to keep

CSS positioning is not about moving elements around the screen. It is about declaring which rectangle an element measures itself against, then removing it from — or keeping it in — the normal flow. Every positioning decision is a containing block decision first.

When something lands in the wrong place, the question is not "why isn't my top working?" The question is "which box does the browser think is the containing block right now?" Walk up the DOM: look for the first non-static ancestor for absolute elements, look for transforms for fixed elements, look for overflow properties for sticky elements. The answer is almost always in that walk.

The four values are a short vocabulary. The containing block is the grammar. Learn the grammar, and the vocabulary takes care of itself.
