The Box Model Is Arithmetic

Every layout problem has the same root: declared dimensions don't mean what you think. Here's how the four-layer calculation actually works.

Try it — change box-sizing and watch the box grow or stay put

1
2
3
box-sizing
padding
border-width
.container {
  display: block;
  box-sizing: content-box;
  padding: 24px;
  border-width: 4px;
}

Set width: 100% on an element, add padding: 1rem, and the element overflows its container. The layout is not broken — the arithmetic is working exactly as CSS2 specified it. That specification, still the default today, adds padding and border on top of whatever width you declared. A 300 px box with 16 px of padding on each side becomes 332 px wide. The number you wrote means less than you thought.

The CSS box model is a calculation rule, not a vocabulary list. Four layers wrap every element — content, padding, border, margin — and the order in which they are measured determines whether your declared dimensions mean what you intended. Getting that arithmetic into your hands is what this issue is for.

The four layers, measured

Every block-level element generates a rectangular box. Working outward from the centre: the content area (where text and child elements live), padding (transparent space between content and border), border (a drawn edge with colour, style, and width), and margin (transparent space outside the border that pushes other elements away).

In the browser's default model, box-sizing: content-box, the width and height properties describe only the content area. Everything else is additive. Given this rule:

.card {
  width: 300px;
  padding: 20px;
  border: 4px solid currentColor;
}

The element occupies 348 px of horizontal space: 300 (content) + 40 (padding left and right) + 8 (border left and right). Margin is not counted in the element's own footprint — it pushes neighbours away but is not part of the rendered edge. If that .card sits inside a 300 px container, it overflows by 48 px. The container did not shrink; the arithmetic added up correctly and the result exceeded the available space.

box-sizing

The box-sizing property changes what the declared width and height measure. Its two meaningful values are content-box (the default) and border-box.

/* The industry-standard reset */
*,
*::before,
*::after {
  box-sizing: border-box;
}

With border-box, padding and border are absorbed into the declared dimensions. That same 300 px card with 20 px padding and a 4 px border will have a content area of 252 px, but its total rendered width stays exactly 300 px. Margin is never absorbed — it remains outside the box in both models. Paul Irish popularised this universal reset around 2012; every current browser supports border-box unprefixed. The vendor-prefixed forms (-webkit-box-sizing, -moz-box-sizing) are historical artefacts no modern codebase needs.

Margin collapsing

Margins between adjacent vertical elements do not add together — they collapse to the larger of the two values. This is not a bug. It is a deliberate rule from the CSS2 specification, designed to keep paragraph spacing consistent regardless of nesting. It is also one of the most reliably surprising things in CSS.

Given two sibling paragraphs, the first with margin-bottom: 24px and the second with margin-top: 16px, the space between them is 24 px, not 40 px. The smaller margin collapses into the larger. The same principle applies between a parent and its first or last child: if nothing separates the parent's top edge from the child's top edge — no border, no padding, no formatting context — the child's margin-top collapses with the parent's margin-top and escapes upward out of the parent.

Two things make this particularly tricky. First, it is asymmetric: horizontal margins never collapse, only vertical ones in normal block flow. Second, collapsing does not happen inside a flex or grid formatting context. Adding display: flex to a container causes its children's margins to sum normally again — which can quietly change your spacing if you were relying on collapse to keep gaps consistent.

/* Collapsing — gap between siblings is 24px, not 40px */
.sibling-a { margin-bottom: 24px; }
.sibling-b { margin-top: 16px; }

/* No collapsing — gap is 40px */
.flex-parent { display: flex; flex-direction: column; }
.flex-parent .sibling-a { margin-bottom: 24px; }
.flex-parent .sibling-b { margin-top: 16px; }

To prevent parent-child margin collapse, the most reliable technique is adding a border or padding to the parent. Even padding-top: 1px creates the separation the browser needs to stop the child's margin from escaping. Establishing a new block formatting context — with overflow: hidden, display: flow-root, or a flex or grid container — also prevents collapse.

outline is not part of the box

A common debugging mistake is confusing outline with border. They look similar in the browser, but outline is drawn outside the border edge and takes up no space in the layout. It does not affect the box model calculation — adding a thick outline does not shift surrounding elements. That makes it useful for debugging (it shows the box without disturbing the layout) and for focus indicators (the ring appears without causing reflow).

/* Debug without affecting layout */
* { outline: 2px solid tomato; }

/* Focus ring — no reflow */
.focused { outline: 3px solid royalblue; outline-offset: 2px; }

Percentage padding

Percentage values for padding are calculated against the element's containing block width — not its height, and not the axis the padding is on. padding-top: 50% is 50% of the container's width, not its height. This is the rule that makes the classic aspect-ratio padding hack work: a box with padding-top: 56.25% and no explicit height will always be 16:9 relative to its container width. The CSS aspect-ratio property has largely replaced this technique, but understanding why the hack worked explains something real about how the box model handles percentages.

Where the spec is heading

The four-layer model is not a closed topic. Two directions are worth watching: logical properties and intrinsic sizing keywords.

Logical properties replace physical directions (top, right, bottom, left) with writing-mode-relative ones. Instead of margin-top and margin-bottom, you write margin-block-start and margin-block-end, or the shorthand margin-block. Instead of margin-left and margin-right, you write margin-inline. These properties adapt automatically to vertical writing modes and right-to-left scripts, which physical properties cannot do without explicit overrides. Browser support is good across current engines; if your audience includes older browsers, check the compatibility table before replacing physical shorthands wholesale.

/* Physical — does not adapt to writing mode */
.card {
  margin-top: 1.5rem;
  margin-bottom: 1.5rem;
  padding-left: 1rem;
  padding-right: 1rem;
}

/* Logical — adapts to writing mode and text direction */
.card {
  margin-block: 1.5rem;
  padding-inline: 1rem;
}

Intrinsic sizing keywords — min-content, max-content, fit-content — extend what you can set on width and height, letting the content itself determine dimensions rather than a fixed number. They are defined in the CSS Box Sizing Level 3 and Level 4 specifications. Support is uneven in older environments; treat them as progressive enhancement for now.

The box model has been the ground under every layout technique CSS has ever produced — floats, positioning, flexbox, grid, all of it. Getting its arithmetic right is not a beginner step to move past. It is the thing that makes the rest legible.
