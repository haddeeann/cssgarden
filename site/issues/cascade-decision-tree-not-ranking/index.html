The Cascade Is a Decision Tree, Not a Ranking

Specificity is only question four in a five-step algorithm. Understanding the full sequence explains every rule that ever felt like it shouldn't have won.

Every browser resolves style conflicts by running the same five-question algorithm — and specificity, the one step most developers know by name, is only question four. The rules that feel mysterious — why !important sometimes loses, why a low-specificity reset can beat a carefully crafted component style — stop being mysterious the moment you see the full sequence.

Five questions, in order

The cascade is a tiebreaker, not a ranking. The browser works through its questions one at a time and stops the moment one produces a single winner. If you've ever added a more-specific selector and still lost the fight, the fight was already over at an earlier step.

The five steps, in the order the browser applies them:

  • Relevance — does this declaration apply to this element at this moment? (Media queries, selector matching.)
  • Origin and importance — where did the rule come from, and is it marked !important?
  • Cascade layers — if @layer is involved, which layer takes priority?
  • Specificity — how targeted is the selector?
  • Order of appearance — when everything else ties, the last declaration wins.

Relevance is a filter, not a contest. Once irrelevant declarations are removed, the remaining four steps are the actual competition. Most CSS education teaches steps four and five as if they were the whole game.

Origin comes first — and importance flips it

Before specificity gets a vote, the browser asks where a declaration came from. There are three origins: the browser's built-in stylesheet (user-agent), a stylesheet the reader has applied themselves (user), and the stylesheets you write (author). In normal priority, author beats user beats user-agent. This is why your CSS overrides browser defaults without any fuss.

!important doesn't just amplify a rule — it moves the rule into a separate, inverted origin stack. In the important layer, the order reverses: user-agent-important beats user-important beats author-important. A user stylesheet marked !important can override your author !important, by design, because user overrides exist to support accessibility needs that authors shouldn't be able to trample.

/* Author stylesheet — wins in normal origin */
p { color: navy; }

/* User stylesheet — loses to author in normal origin */
p { color: black; }

/* User stylesheet with !important — beats author !important */
p { color: black !important; }

/* Author stylesheet with !important — loses to user !important */
p { color: navy !important; }

The practical consequence: when you reach for !important to force a style, you've entered a competition where user agents and user stylesheets outrank you. More immediately, you've created a rule that can only be overridden by another !important from an equal or higher origin — which is how specificity wars escalate into !important wars.

The three-column specificity score

Specificity is calculated as three independent columns: IDs, then class selectors / attribute selectors / pseudo-classes, then element selectors / pseudo-elements. A higher number in the leftmost column always wins, regardless of the other columns. 0-1-0 (one class) beats 0-0-10 (ten element selectors) because the columns never carry over.

/* 0-0-1 — one element selector */
p { color: gray; }

/* 0-1-0 — one class selector, beats the above */
.intro { color: teal; }

/* 1-0-0 — one ID selector, beats both */
#hero { color: crimson; }

/* Inline style: 1-0-0-0 — a fourth column, beats all of the above */
/* <p style="color: gold"> */

One edge worth knowing: :is(), :has(), and :not() take the specificity of their most specific argument. :is(#hero, p) scores 1-0-0 even when the element it matches is a plain p, because the ID argument sets the ceiling.

Where cascade layers fit in

Cascade layers, introduced with @layer, sit between origin and specificity in the algorithm. They were designed to solve exactly the problem specificity wars create: a way to declare that an entire group of styles should defer to another group, regardless of how specific the selectors are.

@layer reset, base, components, utilities;

@layer reset {
  * { box-sizing: border-box; margin: 0; }
}

@layer components {
  .card { padding: 1rem; background: white; }
}

@layer utilities {
  .mt-4 { margin-top: 1rem; }
}

Layers declared later in the list take priority over earlier ones — so utilities beats components beats base beats reset, regardless of specificity. A zero-specificity utility rule in utilities beats a high-specificity component rule in components because the layer comparison is resolved before specificity is consulted.

The unlayered rule always wins

The most counterintuitive behavior in the cascade layers spec: any style not inside a @layer block beats any style that is inside one, regardless of specificity or order. Unlayered styles sit above all named layers in the implicit layer stack.

@layer components {
  /* 1-0-0 specificity — still loses */
  #hero .card h2 { color: navy; }
}

/* 0-1-0 specificity — wins because it's unlayered */
.headline { color: crimson; }

This is intentional. Third-party layered libraries can never accidentally override your unlayered page styles, no matter how specific their selectors are. The catch: if you adopt @layer partway through a codebase, any legacy unlayered CSS will silently outrank everything you put in layers.

Browser support for @layer

Cascade layers landed in Chrome, Edge, and Firefox in early 2022. The support cliff is hard: browsers that don't support @layer ignore the at-rule entirely, which means styles inside layers are dropped — not degraded, dropped. If you're using layers where older browser support matters, put critical fallback styles outside any layer.

A sixth step on the horizon

@scope, defined in CSS Cascading and Inheritance Level 6, adds scoping proximity as a new cascade step between layers and specificity. When two rules share the same origin, layer, and specificity, the one whose scope root is closer in the DOM tree wins. This lets you write component styles that naturally beat global styles for elements inside that component, without inflating specificity.

@scope (.card) {
  /* Wins over a global `p` rule for paragraphs inside .card,
     by proximity — not by specificity */
  p { color: #333; line-height: 1.6; }
}

@scope sits at approximately 91% browser support as of late 2025, though it's still part of a living specification and behavior details may continue to settle. It's worth experimenting with on non-critical paths — scoping proximity is the most significant addition to the cascade algorithm in years.

The mental model to carry forward

The cascade is a decision tree that stops as soon as it finds a winner. Origin and importance are the first gate — the only one !important affects, by inverting the origin order rather than amplifying a rule's weight. Layers are the second gate, where unlayered styles sit above all named layers. Specificity is the third gate, where the three-column score is compared. Order of appearance is the fallback when everything else ties.

Knowing this sequence changes how you debug. When a rule loses unexpectedly, the question isn't "is my selector specific enough?" — it's "at which step did it lose?" A rule with an ID selector that still loses probably lost at origin or layer, not at specificity. Adding more classes to the selector won't fix it, because the browser never reached the specificity comparison.

The practical upshot for a design system or component library: put your library styles inside @layer and leave consumer overrides unlayered. Specificity becomes largely irrelevant within the library — layers handle the priority — and consumers get clean, predictable wins without writing a single !important.
