Block, Inline, Inline-Block: The Display Model You Actually Need

The display property doesn't style a box — it enrolls one in a formatting context. That distinction explains the four-pixel gap, the baseline drop, and every other quirk the comparison tables can't.

Every time a developer writes display: inline-block and then spends twenty minutes hunting a mysterious four-pixel gap, they are paying the tax for not knowing what display actually declares. It does not style a box. It enrolls a box in a formatting context — and that single distinction explains every quirk that comparison tables leave dangling.

Two types, one property

The display property sets two things at once. The outer type decides how a box participates in its parent's layout. The inner type decides how that box lays out its own children. The classic single-value keywords are shorthands for both.

The CSS Display Module Level 3 spec makes this explicit with a two-value syntax: block is shorthand for block flow, and inline-block is shorthand for inline flow-root. Those longer forms are not new features — they are the spec finally saying out loud what the single-value keywords have always meant. Browser support for the two-value syntax is solid in modern engines, but the single-value keywords remain the safe production choice.

Reading inline flow-root is immediately clearer than reading inline-block: the outer type is inline, the inner type is flow-root, meaning the box establishes a new block formatting context (BFC) inside itself. That is not a hybrid. It is an inline box on the outside and a self-contained block world on the inside. Every inline-block quirk you have ever encountered lives in that gap between outside and inside.

Outer type: block

A box with an outer type of block participates in a block formatting context. It stretches to fill its containing block's inline size, breaks onto its own line before and after, and treats margin: auto on the inline axis as a genuine centering instruction. Width, height, and all four margin values are fully respected. 

.card {
  display: block;   /* outer: block, inner: flow */
  width: 40ch;
  margin-inline: auto; /* works: block layout resolves auto margins */
}

Outer type: inline

A box with an outer type of inline participates in an inline formatting context. It sits on the line alongside text and other inline boxes. It does not accept width or height — the inline formatting context has no mechanism to resolve them. Horizontal margins and padding work. Vertical padding renders (the background color extends above and below), but it does not push adjacent lines apart, because inline boxes do not contribute to block-axis layout. This surprises every developer who tries to pad a link into a button shape and watches it bleed through the lines above and below. 

a.tag {
  display: inline;
  padding-block: 0.5em; /* visible, but does not move surrounding lines */
  background: oklch(90% 0.1 150);
}

One quiet exception: replaced elements — <img>, <input>, <video> — accept width and height even at display: inline. The spec grants replaced elements this ability regardless of display type, because their intrinsic dimensions come from an external resource rather than from flow layout. This is why you can resize an image with width: 100% without changing its display value. It is not an inconsistency; it is a separate rule that most introductory articles forget to mention.

Outer type: inline — inner type: flow-root (a.k.a. inline-block)

This is where the model earns its keep. The outer type is still inline — the box sits on a line, respects whitespace, aligns to a baseline. But the inner type is flow-root, which means the box establishes a new BFC for its children. Inside that boundary, block layout rules apply: width and height are respected, the box shrink-wraps its content if no explicit size is set, and floated children are contained rather than escaping into the parent. 

.badge {
  display: inline-block; /* inline flow-root */
  padding: 0.25em 0.75em;
  width: 8ch;            /* works: inner BFC resolves this */
  vertical-align: middle;
}

The whitespace gap, explained at the root

Place two inline-block elements next to each other in HTML source with a newline between the closing and opening tags, and a gap appears. It is not a margin, not a border, and not a browser bug. It is a space character.

The inline formatting context treats HTML source whitespace — spaces, tabs, newlines between tags — as text content. It collapses runs of whitespace into a single space glyph and renders it. That glyph has a width determined by the current font, typically around 0.25em. Every workaround for the gap is a way to either eliminate that space character or make it invisible:

  • Remove the whitespace between closing and opening tags in the HTML source (works, but is fragile and unreadable).
  • Set font-size: 0 on the parent, then restore font-size on the children (the space glyph renders at zero width).
  • Use a negative margin equal to the gap width (brittle across fonts and sizes).

The durable fix is to stop using inline-block for multi-column layout and reach for Flexbox or Grid instead — both establish inner formatting contexts that do not collapse whitespace between children. That said, inline-block remains the right tool for inline-sized containers that need explicit dimensions, like icon badges or code labels sitting inside a paragraph.

The baseline trap

Because inline-block has an outer type of inline, it aligns to the line's baseline by default. For a box that contains text, the baseline is the text baseline — sensible. For a box with no text content, the spec defines the baseline as the bottom margin edge of the box. That means an empty inline-block sits with its bottom edge on the baseline, dropping it well below any text siblings on the same line. 

/* Empty inline-block sinks to baseline — often not what you want */
.icon-box {
  display: inline-block;
  width: 1.5em;
  height: 1.5em;
}

/* Fix: align to middle or top instead */
.icon-box {
  display: inline-block;
  width: 1.5em;
  height: 1.5em;
  vertical-align: middle;
}

Every browser implements the same spec rule here. The fix is always an explicit vertical-align value. middle is the most common choice for icon-adjacent text; top works when you want the box flush with the tallest element on the line.

A short field guide

Three values, three situations. The model makes the choice obvious once you know what you are actually choosing.

  • Use block when the element should occupy a full row, respond to explicit widths and heights, and support margin: auto centering. Structural containers — sections, cards, headings, paragraphs — belong here.
  • Use inline when the element should flow with text and you do not need to control its block-axis size. Emphasis spans, links inside prose, abbreviations — these are inline by nature and should stay that way.
  • Use inline-block when the element must sit inline with text and accept explicit dimensions or contain block-level children. Badges, code labels, and icon wrappers are the canonical cases. Account for the whitespace gap and set vertical-align deliberately.

The comparison table — starts new line? accepts width? accepts margin? — is a useful cheat sheet once you have the model. Without the model, it is just a list of symptoms with no way to reason about edge cases. The edge cases are where the time goes.

Flexbox and Grid each introduce their own inner display types — flex and grid — which replace the inline formatting context inside the container entirely. The outer type still applies: a display: flex container is a block-level box on the outside. That is a thread for another issue.
