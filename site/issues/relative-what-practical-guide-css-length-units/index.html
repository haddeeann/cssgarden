Relative to What? A Practical Guide to CSS Length Units

Every CSS length is an answer to one question: relative to what? Pick the wrong anchor and your type snowballs, your hero bleeds off the screen, and your layout drifts. Pick the right one and the whole system snaps into place.

Every CSS length is an answer to one question: relative to what? Get that question wrong and your layout drifts, your type snowballs in nested components, and your full-screen hero bleeds off the bottom of every iPhone. Get it right and the whole system snaps into place.

Six units carry most of the work — px, rem, em, %, vw, and vh — and each one names a different anchor point. The confusion is rarely about memorising definitions. It is about knowing which anchor is in play, and whether that anchor can shift underneath you.

Fixed ground: what px actually means

px is the only unit on this list that answers "relative to what?" with "nothing." It is an absolute unit, pinned to a physical reference point — one ninety-sixth of a CSS inch, then multiplied by the device pixel ratio on high-density screens. It does not move when the viewport changes. It does not move when a user raises their browser's default font size in preferences.

That last point is the accessibility trap. Browsers ship with a default font size — typically 16px — that users can raise to 20px or 24px if they need larger text. When you set font-size: 16px, you override that preference entirely. The user asked for bigger type; you said no. WCAG success criterion 1.4.4 (Resize Text) exists precisely because of this pattern. px is fine for borders, shadows, and fine-grained detail. For font sizes, it locks out the people who need flexibility most.

px — absolute, device-anchored

/* Appropriate: fine detail that should not scale */
.card {
  border: 1px solid #ddd;
  border-radius: 4px;
  box-shadow: 0 2px 8px rgba(0,0,0,.12);
}

/* Risky: ignores user font preferences */
.card-title {
  font-size: 20px; /* a user who set 20px as their default gets no benefit */
}

The compounding trap: em versus rem

rem stands for "root em." It resolves against the font size of the <html> element — one fixed anchor for the whole document. em, by contrast, resolves against the font size of the current element, which may itself be inherited or already expressed in em. That difference is everything.

Imagine a card component where the base font size is 1rem (16px). You style the nested list inside it with font-size: 0.9em — sensible enough. That list contains another list, also 0.9em. The second level is now 0.9 × 0.9 = 0.81rem, or about 13px. Add a third level and you are at 11.7px. The type has not scaled gracefully; it has quietly collapsed. This is the compounding problem, and it is the single most common source of mysterious type drift in component-heavy codebases.

rem — always anchored to the root

/* Safe: no matter how deeply nested, 1rem is always 16px
   (or whatever the user's root preference is) */
h2    { font-size: 1.5rem;   }
p     { font-size: 1rem;     }
small { font-size: 0.875rem; }

em — anchored to the current element's font size

/* Dangerous for font-size in nested contexts */
.list .list { /* 0.9 × 0.9 = 0.81em of root — and shrinking */ }

/* But exactly right for spacing that should scale with local type */
.card {
  font-size: 1rem;   /* set once in rem */
  padding: 1.25em;   /* scales with the card's own font size */
  gap: 0.75em;
}

The practical rule: use rem for font sizes, em for padding, margin, and gap. Spacing in em scales proportionally with the component's type size — shrink the font and the padding follows. That is the behaviour you want. Set font sizes in em inside nested components, though, and the cascade multiplies values until you lose control. One subtlety worth noting: when em appears on non-font properties such as padding, it resolves against the element's own computed font size, not the parent's. This is usually what you want, but it differs from what em does on font-size itself, where it inherits from the parent before resolving.

Percentages: the anchor changes with the property

MDN puts this plainly: percentages are "always relative to some other value." What it does not say loudly enough is that which value depends entirely on the property being set — and the answer is sometimes surprising.

width: 50% is relative to the parent element's width. Intuitive. height: 50% is relative to the parent element's height — but only if the parent has an explicit height set; otherwise it collapses to zero. Less intuitive. Here is the genuine gotcha: margin-top: 10% is relative to the parent element's width, not its height. The same is true of padding-top and padding-bottom. This is not a bug; it is how the spec defines percentage margins and padding, and it is the mechanism behind the old aspect-ratio-box trick (padding-top: 56.25% for a 16:9 container). Reach for margin-top: 10% expecting ten percent of the container's height, and you will be confused by what you get.

% — relative to a property-specific ancestor value

.layout {
  width: 80%;       /* 80% of parent's width — predictable */
  height: 50%;      /* 50% of parent's height — only works if parent has explicit height */
  margin-top: 5%;   /* 5% of parent's WIDTH, not height */
  padding-top: 5%;  /* same: parent's width */
}

For layout proportions — column widths, image sizes, container constraints — % is the right tool. Keep the "relative to what?" question close at hand, because the answer is not always the axis you expect.

Viewport units and the mobile problem

vw and vh are each one percent of the viewport's width and height. They sound perfect for full-bleed layouts. On desktop they mostly are. On mobile, vh has a well-documented trap that catches nearly every developer who reaches for height: 100vh on a hero section.

Mobile browsers — Safari on iOS being the most prominent — include the browser chrome (address bar and toolbar) in the initial viewport height calculation. When the user scrolls and the toolbar retracts, the viewport grows, but elements already sized to 100vh were measured against the smaller value. A 100vh hero is slightly taller than the visible screen on first load, producing an overflow that looks like a layout bug.

The CSS Working Group addressed this with three new units, now supported in nearly all modern browsers: svh (small viewport height — the viewport with browser UI fully visible, the smallest it will ever be), lvh (large viewport height — UI hidden, the largest it can be), and dvh (dynamic viewport height — updates in real time as the UI shows and hides). For a hero that should fill the visible screen on load, svh is the safe choice. For a sticky element that should fill the screen after scrolling, dvh is closer to correct, though it can cause reflow jank as the toolbar animates. Firefox on iOS and most in-app browsers (Instagram, Facebook) still do not handle svh and lvh correctly, so a vh fallback before the new unit remains good practice.

vw / vh — viewport-relative, with caveats

.hero {
  /* Fallback for browsers without svh support */
  height: 100vh;
  /* Safer on mobile: sized to viewport with UI visible */
  height: 100svh;
}

/* Avoid on desktop: vw includes scrollbar width,
   triggering a horizontal overflow */
.full-width {
  width: 100vw; /* can produce a horizontal scrollbar */
  width: 100%;  /* block elements: use this instead */
}

One more vw edge case: on desktop browsers, 100vw includes the scrollbar width while the document flow does not. Setting width: 100vw on a block element will almost always produce a horizontal scrollbar. The correct pattern is width: 100%.

A decision rule, not a glossary

Each unit names an anchor. The right unit is the one whose anchor matches your intent:

  • rem for font sizes. One anchor, the root, shared by the whole document. Respects user preferences. Never compounds.
  • em for component-local spacing. Padding, margin, and gap in em scale proportionally with the component's own type size — exactly the behaviour you want from a self-contained component.
  • % for layout proportions. Column widths, container constraints, image sizing. Keep "relative to what?" in mind, especially for vertical properties.
  • vw / vh with new-unit fallbacks for viewport-filling geometry. Full-bleed sections, sticky overlays, anything that responds to screen size rather than content. Use svh / dvh / lvh with a vh fallback for mobile reliability.
  • px for fine, fixed detail. Borders, shadows, outlines — things that should not scale and do not affect accessibility when they stay fixed.

px is the stone path — fixed, unmoved by weather. rem is the hedge line — consistent across the whole plot, trimmed to one reference height. em is the groundcover — filling space in proportion to whatever grows beside it. % is the bed that expands with the plot. And vh / vw are the walls — they define the boundary, but on mobile those walls move more than you expect. Know which material you are working with, and the layout tends to hold.
