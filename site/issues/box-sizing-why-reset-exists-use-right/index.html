Box-Sizing: Why the Reset Exists and How to Use It Right

The default CSS box model adds padding and border on top of whatever width you declare. One property — and one reset pattern — fixes that permanently.

Try it — change box-sizing and watch the element's rendered width

padding
border-width
.container {
  display: block;
  box-sizing: content-box;
  padding: 20px;
  border-width: 5px;
}

Set a div to width: 300px, add padding: 20px and a border: 5px solid, and the element is now 350 pixels wide — not 300. That gap between intention and result is the default CSS box model, and it has been causing layout bugs since the first stylesheet was written.

The property that closes that gap is box-sizing. It has exactly two meaningful values. One is the default, and almost no one wants it. Understanding why — mathematically, not just by convention — is what makes the standard reset feel inevitable rather than arbitrary.

What the browser is actually computing

Every element is a stack of four nested regions: content, padding, border, margin. The box-sizing property controls which of those regions the width and height declarations measure. Margins are never part of that measurement — not in either value, not in any browser, not ever. That last point surprises even experienced developers, so it is worth stating plainly before moving on.

box-sizing: content-box — the default

The W3C specified content-box as the default because it maps cleanly to the original box model: width describes the content area, and everything else is added outside it. This was not a mistake or an oversight — it was a deliberate choice to keep the content dimension independent of its decoration.

The math is additive:

/* Declared */
width: 300px;
padding: 20px;
border: 5px solid;

/* Rendered width */
300 + 20 + 20 + 5 + 5 = 350px

The content area is exactly 300 px. The element occupies 350 px of space. Put two such elements side by side inside a 700 px container expecting them to fit, and they won't — they overflow by 100 px.

box-sizing: border-box — the intuitive one

With border-box, the declared width becomes the outer edge of the border. Padding and border are compressed inward, reducing the content area. The element never grows beyond what you wrote. 

/* Declared */
box-sizing: border-box;
width: 300px;
padding: 20px;
border: 5px solid;

/* Rendered width */
300px — always

/* Content area */
300 - 20 - 20 - 5 - 5 = 250px

The element is 300 px wide. The content area shrinks to accommodate the decoration. This is what most people mean when they write width: 300px. It is also — interestingly — the box model that old Internet Explorer used in quirks mode, which is why CSS-Tricks once called border-box the "restoration of the quirky way." The intuition predates the spec.

One thing border-box still cannot do: include the margin. Margin lives entirely outside the border edge in both values, always. Add margin: 10px to the element above and the occupied space becomes 320 px, but the element's own box is still 300 px. This is the single most common misconception about the property — that border-box somehow accounts for "everything." It accounts for padding and border. Margin is the gap between boxes, not a part of any box.

Three ways to apply it, and why they differ

The property is not inherited by default. Setting it on a parent does nothing for the children unless you explicitly make it cascade. That single fact explains the entire history of how developers have applied the reset.

The universal reset — direct and blunt

Paul Irish's 2012 essay popularized this pattern, and it remains the most common version in tutorials: 

* {
  box-sizing: border-box;
}

The * selector matches every element directly, which is why it works despite box-sizing not being inherited. Every element gets its own explicit declaration. Simple, effective, and sufficient for most small-to-medium projects.

The catch: because * applies directly to every element, a third-party widget that sets box-sizing: content-box on its root element will have that declaration immediately overridden on its children by *. The widget cannot opt itself out. For projects that embed third-party components, this matters.

The pseudo-element extension is also worth including. The * selector does not automatically cover ::before and ::after in all implementations, so the complete version is: 

*,
*::before,
*::after {
  box-sizing: border-box;
}

The inherit pattern — flexible and composable

A later refinement sets the value on html and then tells every other element to inherit it: 

html {
  box-sizing: border-box;
}

*,
*::before,
*::after {
  box-sizing: inherit;
}

This looks almost identical in everyday use, but the cascade behavior differs in one important way. Because children now inherit rather than receive a direct declaration, a third-party widget can set box-sizing: content-box on its own root element and have that value cascade correctly through all of its children — because inherit picks up whatever the parent has, and the parent is now content-box. 

/* Third-party widget can now safely opt out */
.widget {
  box-sizing: content-box;
  /* All .widget children will inherit content-box */
}

For most personal projects and small applications, the difference is academic. For component libraries, design systems, or any project that embeds external UI code, the inherit pattern is the safer default.

Where it already applies without you asking

One practical argument for the global reset is consistency: many browsers already apply border-box to form controls — <input>, <select>, <button> — in their default user-agent stylesheets. Without a reset, form elements and div elements follow different box models by default. Setting border-box globally makes the page consistent with what browsers already do for the elements that handle user input.

A note on images: applying border-box to <img> elements means that adding a border to an image will scale the image down to fit inside the declared width. Usually fine — but if you need pixel-perfect dimensions on the image content itself, keep it in mind.

One value you may encounter in older posts is padding-box — a third option that would have included padding but not border in the width calculation. It was removed from the CSS Box Sizing Level 3 specification before it shipped in any stable browser. It does not exist in any current implementation. If a tutorial recommends it, the tutorial is out of date.

The mental model, restated simply

box-sizing answers one question: when you write width: 400px, what is 400 px measuring?

  • content-box: 400 px is the content area. Padding and border are added outside it. The element grows.
  • border-box: 400 px is the outer edge of the border. Padding and border are subtracted from the inside. The element stays fixed.
  • Neither value: Margin is not included. Margin is the space between elements, not a dimension of any element's box.

The reset is not a workaround for a browser bug. It is a choice to use the model that matches how most people think about width — as the space the element occupies on screen, not the space available to its text. Once that model is in place, percentage widths with pixel padding work, grid columns accept borders without overflowing, and the arithmetic you do on paper matches the arithmetic the browser does. That is the whole argument. Everything else is implementation detail.
