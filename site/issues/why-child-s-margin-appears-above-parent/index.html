Why Your Child's Margin Appears Above the Parent

Every margin-collapsing surprise traces back to one word in the CSS 2.1 spec: adjoining. Understand what breaks adjacency and you understand all the cases at once.

Try it — change the parent, watch the child's margin stop escaping

Set margin-top: 2rem on a child element inside a plain <div> and the space doesn't appear between parent and child — it appears above the parent, pushing the whole box down the page. The child's margin has escaped. This isn't a browser bug to memorize around; it's a direct consequence of one word in the CSS 2.1 specification, and once you see that word clearly, every margin-collapsing surprise becomes predictable.

One word from the spec: adjoining

The CSS 2.1 specification says margins collapse when they are adjoining. Two margins are adjoining when they belong to block-level boxes in the same block formatting context, with no line boxes, no clearance, no padding, and no border separating them. That's the entire model.

The three cases you'll find in every tutorial — adjacent siblings, parent-and-first-child, and empty blocks — aren't three separate rules. They're three situations where the adjoining condition happens to be satisfied. Understand what breaks adjacency, and you understand all of them at once.

Adjacent siblings collapse because nothing sits between the bottom margin of one paragraph and the top margin of the next. They're in the same block formatting context, touching directly. The parent-child case is stranger: a child's margin-top bleeds out through the parent because the parent has no border, no padding, and no content before the child — so the parent's own top margin and the child's top margin are, by the spec's definition, adjoining. They share the same edge. The empty-block case follows the same logic: an element with no height, no padding, and no border has its own top and bottom margins touching each other, so those collapse too, and the resulting margin can then collapse with whatever is adjacent to it.

The historical context makes this feel less arbitrary. The feature was designed for document-flow typography — headings followed by paragraphs, paragraphs followed by block quotes. In that world, you want a heading's bottom margin and a paragraph's top margin to negotiate a single comfortable gap rather than stack. The spec authors were thinking about printed pages, not application layouts. Horizontal margins were intentionally excluded from collapsing because lines of text don't stack sideways.

The block formatting context is the fence

A block formatting context — a BFC — is a region of the page with opaque walls for margin collapse. Margins inside a BFC cannot collapse with margins outside it. Creating a new BFC around or inside an element is how you prevent collapse, and once you know that, every technique you've seen recommended makes immediate sense.

display: flow-root

The cleanest modern way to create a BFC with no side effects. The element behaves exactly like a block box in terms of layout but establishes a new formatting context for its contents. A child's margin can no longer be adjoining to the parent's because the BFC boundary stands between them.

.parent {
  display: flow-root;
}

No clipping, no overflow changes, no effect on the parent's siblings. Reach for this when you want a BFC and nothing else.

overflow: hidden (and its cousins)

Any value of overflow other than visible also creates a BFC — which is why overflow: hidden has been the traditional collapse-stopper. It works for the same reason flow-root works: it establishes a new formatting context. The cost is that it can clip shadows, tooltips, and absolutely-positioned children that extend beyond the box. Older tutorials recommend it by default; prefer flow-root unless you actually want clipping.

.parent {
  overflow: hidden; /* creates a BFC, but clips overflow */
}

border and padding

Adding even 1px of padding-top or border-top to a parent breaks the parent-child collapse — not because of any BFC, but because padding and border now separate the two margins. They are no longer adjoining by the spec's definition. This is the simplest fix for parent-child bleed-through and has no layout side effects when the space is intentional.

.parent {
  padding-top: 1px; /* margins no longer touch */
}

display: flex and display: grid

Flex and grid containers establish a formatting context for their children. Flex and grid items do not participate in margin collapsing with each other or with the container. This is why switching a parent to display: flex silently "fixes" collapsed margins — the formatting context changed, not your margins. If you're reaching for flex or grid purely to stop collapse, flow-root is more honest about intent. If you're already doing flex or grid layout, the collapse prevention comes free.

.parent {
  display: flex;
  flex-direction: column; /* margins between children no longer collapse */
}

When negative margins join the collapse

Negative margins don't follow the simple "largest wins" rule. The arithmetic is different, and it trips up developers who assume symmetry.

When all collapsing margins are positive, the result is the largest single value — a 2rem bottom margin and a 1rem top margin collapse to 2rem. When negative margins are involved, the result is the sum of the largest positive value and the most-negative value. A 2rem positive margin collapsing with a -1rem negative margin produces 1rem. Two negative margins collapsing with each other produce the most-negative value.

/* Collapsed result: 2rem + (−1rem) = 1rem */
.above { margin-bottom: 2rem; }
.below { margin-top: -1rem; }

/* Collapsed result: −2rem (the more negative wins) */
.above { margin-bottom: -1rem; }
.below { margin-top: -2rem; }

Negative margins in a collapsing context are the most fragile scenario in practice. Some behaviors that appear consistent across Chromium and Safari rely on shared implementation details rather than specified behavior. If you're using negative margins to pull elements together, test across browsers and treat the result as potentially brittle.

Edge cases worth keeping in mind

Margin collapsing only applies to block-level boxes in normal flow. Inline-block elements, table cells, absolutely positioned elements, and fixed-position elements are all excluded — their margins never collapse. This is consistent across browsers and is specified in CSS 2.1, but it surprises developers who switch an element's display mode and find the spacing has changed for reasons they didn't anticipate.

The recursive nature of collapsing is worth knowing: a grandchild's margin can collapse through an empty parent into a grandparent if nothing intervenes at either level. The adjoining condition applies transitively. If the parent has no padding, no border, no height, and no line boxes — and the grandparent has the same — the grandchild's margin travels all the way up.

On logical properties: margin-block-start and margin-block-end collapse in the block direction following exactly the same rules as margin-top and margin-bottom in a horizontal writing mode. In a vertical writing mode, the block direction rotates and collapse follows accordingly. The model is consistent — it's always block-direction margins, not specifically vertical ones.

The decision is straightforward once the model is clear. Reach for display: flow-root when you want a BFC without any other layout change — it's semantically precise and has no side effects. Reach for display: flex or display: grid when you're already doing that kind of layout; collapse prevention comes along for free. Add padding or border when the separation is genuinely part of the design. Avoid overflow: hidden unless you want clipping, and avoid negative-margin tricks in collapsing contexts unless you've tested them carefully.

The parent-child bleed-through — the child's margin appearing above the parent — is the most disorienting version of this behavior because the visual result is so far from the intent. But it follows the same rule as everything else: two adjoining margins collapse. Put something between them, or build a fence with a new formatting context, and they stop being adjoining. The space goes where you put it.
