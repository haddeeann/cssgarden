Four Color Formats, Four Different Promises

Hex and rgb() describe the same gamut. HSL lies about lightness. OKLCH makes a different promise entirely — and it's the one worth building on.

Hex, rgb(), hsl(), and oklch() are not four ways to write the same color. They are four different promises about what a color means — and two of those promises are more honest than the others.

Most developers learn color as hex codes and never fully revisit the decision. That works until it doesn't: until you try to build a consistent type scale where every label reads at the same visual weight, or a button palette where hover states feel evenly stepped, or a theme that needs to stay accessible across its full range. At that point, the format you chose stops being a notation preference and starts being a structural constraint.

The sRGB family — hex and rgb()

Hex codes and rgb() are the same thing wearing different clothes. Both describe a color as a mixture of red, green, and blue primaries inside the sRGB color space. The difference is purely syntactic.

Hex comes in four variants, all valid in every current browser:

  • #RGB — three digits, each expanded to two (#F0A becomes #FF00AA)
  • #RRGGBB — the familiar six-digit form
  • #RGBA — four digits, the fourth being alpha (#F0A8 means roughly 53% opacity)
  • #RRGGBBAA — eight digits, full precision with alpha channel
/* All four hex variants — same color family, different precision */
color: #C0F;          /* #CC00FF shorthand */
color: #CC00FF;       /* explicit 6-digit */
color: #CC00FFA0;     /* 8-digit with ~63% alpha */
color: #C0FA;         /* 4-digit shorthand of the above */

The rgb() function covers the same ground. CSS Color Level 4 introduced a cleaner space-separated syntax alongside the older comma form — both are valid, though the comma form remains safer when targeting older environments:

rgb() — legacy and modern syntax

/* Legacy comma syntax — still valid, still safe */
color: rgba(204, 0, 255, 0.63);

/* Level 4 space-separated syntax */
color: rgb(204 0 255 / 0.63);

/* rgba() is now an alias for rgb() — they are identical */
color: rgb(204 0 255 / 63%);

The slash separates color channels from the alpha value. rgba() is not a separate function in Level 4 — it is accepted as an alias, but rgb() handles alpha directly.

Everything in this family lives in sRGB. The gamut is the same regardless of which syntax you use. If you want a more vivid red than sRGB allows, no hex code or rgb() value can get you there.

HSL — the cylindrical illusion

HSL was designed to be more intuitive than RGB, and in one sense it is: hue as a degree on a color wheel, saturation as a percentage of vividness, lightness as a percentage from black to white. The problem is that lightness axis.

HSL's L value is calculated by averaging the minimum and maximum RGB channel values of the equivalent rgb() color. That is a mathematical shortcut, not a model of human vision. The consequence is concrete: a saturated yellow at hsl(60 100% 50%) and a saturated blue at hsl(240 100% 50%) share an identical lightness value, but they look dramatically different in perceived brightness. Yellow reads almost white; blue reads much darker. Your eyes are not wrong — the HSL lightness number is.

hsl() — syntax and the lightness caveat

/* These share L: 50%, but look nothing like the same brightness */
color: hsl(60 100% 50%);   /* vivid yellow — reads very bright */
color: hsl(240 100% 50%);  /* vivid blue  — reads much darker */

/* Level 4 space-separated form (no commas) */
color: hsl(240 100% 50% / 0.8);

HSL is still sRGB under the hood — cylindrical-coordinate sRGB. Same gamut, different axis arrangement, with a lightness axis that reflects the RGB model's geometry rather than perceptual reality.

For quick color picking, HSL is genuinely friendlier than raw rgb(). For building accessible color systems — where you need to guarantee that a text color has sufficient contrast against its background across a range of hues — HSL's lightness value will mislead you. Two tokens with the same L will fail contrast checks at different rates depending on their hue.

OKLCH — a different underlying model

OKLCH is not a new syntax for sRGB. It is a different color space, built on a perceptually uniform model: equal numeric steps in its lightness channel correspond to approximately equal perceived changes in brightness, regardless of hue.

The three channels:

  • L — lightness, from 0 (black) to 1 (white). A value of 0.5 is genuinely mid-brightness to a human eye across all hues.
  • C — chroma, the vividness of the color. It starts at 0 (gray) with no fixed upper bound — the maximum depends on the hue and what the display can render.
  • H — hue angle in degrees, the same wheel concept as HSL but mapped to a perceptually corrected space.

oklch() — syntax and fallback pattern

/* oklch(lightness chroma hue) */
color: oklch(0.55 0.22 264);         /* a vivid blue */
color: oklch(0.55 0.22 264 / 0.8);  /* same, with alpha */

/* Fallback for browsers before Chrome 111 / Firefox 128 / Safari 16.4 */
color: #5500ff;                /* sRGB fallback first */
color: oklch(0.45 0.28 264);   /* capable browsers use this */

Declare the hex or rgb() value first, then the oklch() value. Browsers that do not understand oklch() ignore the second declaration and keep the first. Browsers that do understand it override with the richer value.

OKLCH reached Baseline "Widely Available" status with Chrome 111, Firefox 128, and Safari 16.4. For new projects not targeting older browser versions, it is safe to use as the primary format with hex fallbacks where needed.

The gamut question — and what clipping means in practice

OKLCH can describe colors that do not exist inside the sRGB gamut. On a Display-P3 screen, those colors are real and renderable. On a standard sRGB display, the browser clips them to the nearest displayable color — silently, without an error.

Clipping is not always dramatic. A slightly out-of-gamut value might clip to something barely distinguishable from the intended color. But at high chroma values — particularly in the red and green regions of the hue wheel — clipping can shift the apparent hue noticeably. Test your OKLCH values on an sRGB display as well as a wide-gamut one, and use the color-gamut media feature when the distinction matters:

/* Safe sRGB value for all displays */
.button {
  background: oklch(0.55 0.18 145);   /* moderate chroma, sRGB-safe green */
}

/* Richer value served only to P3-capable displays */
@media (color-gamut: p3) {
  .button {
    background: oklch(0.55 0.28 145); /* higher chroma, genuinely vivid */
  }
}

This pattern gives every display the best color it can render without asking sRGB screens to approximate something they cannot show accurately.

The same perceptual uniformity that makes OKLCH useful for lightness scales also makes it the right interpolation space for color-mix(). Mixing two colors in OKLCH produces a midpoint that looks like a midpoint — hue, lightness, and vividness all step evenly. Mixing in sRGB often produces a muddy or unexpectedly dark intermediate, because the geometry of the space does not match the geometry of perception.

/* color-mix() using oklch as the interpolation space */
color: color-mix(in oklch, oklch(0.6 0.2 30), oklch(0.6 0.2 270));

The relative color syntax — oklch(from var(--brand) l c calc(h + 30)) — extends this further, letting you derive an entire palette from a single token by adjusting individual channels arithmetically. It only works cleanly when the source format is perceptually uniform. Relative color syntax in HSL carries the same perceptual mismatch problems as HSL itself.

The practical decision: use hex when you are matching a value from a design file or communicating with a tool that outputs hex. Use rgb() when you need sRGB values in code and want readable channel numbers. Use HSL when you need to quickly eyeball a hue and you are not building a system that depends on consistent perceived lightness. Use OKLCH when you are authoring a design system, building accessible color scales, or reaching for colors beyond sRGB — and include a hex fallback until your browser-support floor clears the 2023 threshold. The formats are not interchangeable. Each one is a different promise, and now you know which ones to trust.
