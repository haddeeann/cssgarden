Specificity Is Not a Point Score

Browsers don't add up selector points — they compare three columns, left to right, and stop the moment one differs. Once you see it that way, the rules that seemed arbitrary start making sense.

Two rules target the same element. One uses an ID selector. The other stacks eleven class selectors. According to the "points" model taught in most beginner resources, those eleven classes total 110 points against the ID's 100 — so the classes should win. They don't. The ID wins every time, and understanding why means throwing out the points model entirely.

CSS specificity is the algorithm browsers use to decide which declaration wins when more than one rule targets the same element. The algorithm is not arithmetic. It is a three-column comparison — ID, CLASS, TYPE — evaluated left to right, column by column. The columns never carry over into each other. No quantity of class selectors can ever outweigh a single ID selector, because the moment the ID columns differ, the comparison is over and the class column is never consulted.

That broken intuition — specificity as a numeric score — is the most persistent mistake in CSS education. It causes real damage: selectors that pile up to "win," stylesheets that grow progressively harder to override, and debugging sessions spent on the wrong problem entirely.

The three columns, read left to right

Every selector produces a weight written as three numbers: (ID, CLASS, TYPE). To compare two weights, start at the left. The first column where they differ decides the winner. If all three columns are equal, source order breaks the tie.

TYPE — the rightmost column

Element selectors and pseudo-elements each contribute 1 to the TYPE column. p, div, h2, ::before — all score (0, 0, 1). The universal selector * and all combinators (>, +, ~, a space) contribute nothing — they score (0, 0, 0). This surprises many beginners: div > p is not meaningfully "more specific" than p beyond the extra element.

/* (0, 0, 1) — one element */
p { color: navy; }

/* (0, 0, 2) — two elements */
article p { color: teal; }

/* (0, 0, 0) — combinator adds nothing */
* { color: gray; }

CLASS — the middle column

Class selectors, attribute selectors, and pseudo-classes (except those noted below) each add 1 to the CLASS column. .card scores (0, 1, 0). .card.featured scores (0, 2, 0). A rule at (0, 2, 0) beats any rule at (0, 1, anything) — the middle column is compared first, and the right column is irrelevant once a difference is found.

/* (0, 1, 0) */
.card { background: white; }

/* (0, 2, 0) — wins over the rule above */
.card.featured { background: gold; }

/* (0, 1, 1) — loses to .card.featured; middle column is 1 vs 2 */
.card p { background: ivory; }

ID — the leftmost column

ID selectors add 1 to the leftmost column. #header scores (1, 0, 0). Because the ID column is compared before the others, any rule with even a single ID selector outweighs any rule built entirely from classes and elements — no matter how many.

/* (1, 0, 0) — wins */
#header { font-size: 2rem; }

/* (0, 11, 0) — loses, despite eleven classes */
.a.b.c.d.e.f.g.h.i.j.k { font-size: 1rem; }

This is the example that breaks the points model. Eleven classes at "10 points each" would total 110, beating the ID's supposed 100. But the browser never reaches the class column. The ID column reads 1 versus 0, and the comparison is done.

What sits above the three columns

Inline styles and !important are not part of the three-column selector weight. Beginners routinely fold them in as if they were extra columns — they occupy different layers of the cascade entirely.

Inline styles — written directly on an element via the style attribute — effectively occupy a fourth column above the three-column selector weight. MDN represents this as (1, 0, 0, 0) in four-column notation. They beat any selector-based rule for the same property, regardless of specificity.

!important is not a specificity value at all. It moves a declaration into a separate, higher-priority tier of the cascade — the "important" origin. Two !important declarations are then compared by specificity among themselves, but the mechanism is cascade origin, not selector weight. Treating !important as "infinite specificity" is a useful shorthand, but it obscures what is actually happening and makes cascade layers harder to reason about later.

Inheritance has no specificity

A property that reaches an element through inheritance — because a parent was styled and the child inherited the value — carries no specificity whatsoever. A directly targeted rule with a specificity of (0, 0, 1) will always beat an inherited value, even if the inherited rule had a specificity of (1, 0, 0) on the parent. This is the source of many "why won't my color change?" puzzles, and it is almost never explained clearly in beginner resources.

/* Applied to the parent — specificity (1, 0, 0) */
#page { color: crimson; }

/* Applied directly to the child — specificity (0, 0, 1); wins */
p { color: navy; }

The p element gets navy, not crimson, even though the ID rule has higher specificity. The ID rule never targeted p directly — it targeted a parent. Direct targeting always beats inheritance.

Modern pseudo-classes reshape the game

Three pseudo-classes introduced in recent years change how specificity is calculated in ways that are increasingly central to modern CSS architecture — not edge cases to skip over.

:where() — deliberate zero specificity

:where() always resolves to (0, 0, 0), regardless of what selectors are inside it. This makes it a precision tool for writing base styles and resets that anything can override without a specificity fight.

/* (0, 0, 0) — anything can override this */
:where(h1, h2, h3) { margin-block: 1em; }

/* (0, 0, 1) — wins over the :where() rule above */
h2 { margin-block: 1.5em; }

Design systems use :where() for default component styles precisely because it removes the specificity burden from the consumer. Support is broad across modern browsers.

:is() and :has() — inheriting argument specificity

Unlike :where(), both :is() and :has() take the specificity of their most specific argument. :is(#header, .nav, p) resolves to (1, 0, 0) — the specificity of #header — even if only the p elements are actually matched. The specificity is determined at parse time by the selector list, not by which element matched at runtime.

/* Resolves to (1, 0, 0) — because #header is in the list */
:is(#header, p) { font-size: 1rem; }

/* (0, 0, 1) — loses, even though it looks simpler */
p { font-size: 0.875rem; }

:has() reached Firefox in late 2023 and sits at roughly 92% browser support as of 2024. Its specificity behaviour is consistent across supporting browsers, but legacy environments will not recognise it.

@layer — above the specificity game entirely

Cascade layers, declared with @layer, sit above specificity in the cascade order. A rule in a higher-priority layer beats a rule in a lower-priority layer regardless of selector specificity. A (0, 0, 1) element rule in a higher layer can override a (1, 0, 0) ID rule in a lower layer — something impossible with specificity alone.

@layer base, theme;

@layer base {
  /* (1, 0, 0) — but in the lower-priority layer */
  #page { color: crimson; }
}

@layer theme {
  /* (0, 0, 1) — but in the higher-priority layer; wins */
  p { color: navy; }
}

Cascade layers are supported in all modern browsers but absent from IE and older evergreen versions. If your codebase targets legacy environments, layers are not yet available — but understanding that they sit above specificity prepares you for the architecture shift when they are.

The practical takeaway is a single habit: write selectors as low-specificity as the design requires, and no higher. Reach for :where() when you want a style that anything downstream can override without a fight. Reserve IDs for JavaScript hooks and page landmarks, not styling. And when a rule refuses to apply, check source order and inheritance before assuming specificity is the culprit — the cascade has more moving parts than the specificity column alone.
