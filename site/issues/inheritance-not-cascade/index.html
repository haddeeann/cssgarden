Inheritance Is Not the Cascade

Any explicit declaration beats an inherited value — because inheritance isn't part of the cascade at all. It's what happens after the cascade comes up empty.

Any explicit declaration — even a bare element selector with zero specificity — beats an inherited value. That single fact explains more CSS debugging dead-ends than almost anything else in the language, and it only makes sense once you understand that inheritance is not part of the cascade at all. It is what happens after the cascade comes up empty.

Where inheritance actually lives

The browser resolves a property's value through a sequence of stages. First it runs the cascade: it collects every declaration that could apply to an element, weighs origin, layer, and specificity, and picks a winner. If the cascade produces a value, that value wins — full stop. Inheritance only enters the picture when the cascade finds nothing. At that point, if the property is defined as inherited in the specification, the browser walks up the DOM tree and takes the computed value from the nearest ancestor that has one. If no ancestor has one either, the property falls back to its initial value.

This sequence matters because an inherited value has no specificity at all. It is not a low-specificity declaration — it is not a declaration at all. A browser stylesheet rule like a { color: blue } does not "override" your body { color: green } through some specificity contest. It simply wins because it is an actual declaration, and any declaration beats inheritance. That is why anchor links ignore the text color you set on a parent element: the browser's own stylesheet already supplied a real value, so inheritance never gets a turn.

Thinking of inheritance as "styles cascading downward" is the folk model that causes this confusion. The cascade moves horizontally across competing declarations for a single element. Inheritance moves vertically across the DOM after the cascade has already finished its work.

Why text properties inherit and box properties don't

The split is not arbitrary. Properties defined as inherited are almost entirely typographic: color, font-family, font-size, font-weight, line-height, letter-spacing, text-align, visibility, and their relatives. Properties defined as non-inherited are almost entirely structural: margin, padding, border, width, background, display.

The design intent was ergonomic. You want a paragraph's text — and the text of every em and strong inside it — to share the same typeface and color without redeclaring anything. You do not want every child element to inherit its parent's border or padding; that would make layout compositing nearly impossible. The inherited set was chosen to make documents readable by default. The non-inherited set was chosen to keep boxes predictable.

One important detail about how values travel: what inherits is the computed value, not the specified value. If you write font-size: 2em on a parent, the browser resolves that to an absolute pixel value before passing it to children. The child inherits the pixel number, not the 2em token. This prevents compounding — nested elements do not keep doubling — but it also means a child cannot re-interpret a relative value in its own context. The resolution happened upstream.

/* The parent resolves 2em to, say, 32px.
   The child inherits 32px, not 2em.
   Nesting this further does not compound. */
.parent { font-size: 2em; }
.child  { /* font-size: 32px — inherited computed value */ }

The explicit-defaulting keywords

CSS provides five keywords that do nothing except control which stage of the value pipeline an element uses. They work on any property, inherited or not, and they are the precise tools for overriding inheritance or restoring it deliberately.

inherit

Forces a property to take its computed value from the parent, even if the property would not normally inherit. This is how you make a non-inherited property like border travel down the tree on demand.

.child {
  border: inherit; /* takes the parent's computed border value */
}

initial

Resets a property to the value the CSS specification defines as its initial value — not the browser's stylesheet value, but the spec's own default. For color, the initial value is technically canvastext (a system keyword). For display, it is inline. These are often not what you expect if you are thinking of browser defaults.

.reset {
  color: initial; /* spec initial, not necessarily browser default */
}

unset

Context-sensitive. For inherited properties, unset behaves exactly like inherit. For non-inherited properties, it behaves exactly like initial. It is the keyword that says "do whatever is natural for this property type." Used with the all shorthand, it is a compact way to strip every property back to its natural default in one declaration.

.component {
  all: unset; /* inherited props inherit; non-inherited props go to initial */
}

revert

Rolls back to the value the browser's user-agent stylesheet would have applied, as if your own rules did not exist. Where initial goes to the spec floor, revert goes to the browser floor. For a <button> element, all: revert restores the browser's default button appearance; all: unset strips it to nothing. The distinction matters when you want to coexist with browser defaults rather than erase them.

.prose button {
  all: revert; /* looks like a browser-default button again */
}

revert-layer

The newest keyword, from CSS Cascading and Inheritance Level 5. It rolls back to the value that would have applied from the previous cascade layer, ignoring the current layer's declarations. Outside of @layer, it behaves like revert. Browser support is limited to recent versions — treat it as a progressive enhancement rather than a baseline. It cannot be polyfilled in any meaningful way.

@layer base {
  .card { color: navy; }
}
@layer theme {
  .card { color: revert-layer; } /* falls back to navy from base layer */
}

Debugging with the model in mind

The most common inheritance-related bug looks like this: you set a color or font on a high-level element, and somewhere deep in the tree a component ignores it. The usual culprits, in order of likelihood:

  • A browser stylesheet rule (like a { color: blue }) is supplying an explicit declaration that beats the inherited value. Check the user-agent styles in DevTools.
  • A CSS reset or framework is using initial somewhere, which takes properties to their spec floor rather than inheriting from your design tokens.
  • A component is using all: unset for isolation. That correctly strips non-inherited properties — but color and font also get reset to initial when all is involved, which may not be what you intended.
  • A percentage-based value was resolved upstream. The child inherited a pixel value, not the percentage, so resizing the parent does not change what the child received.

DevTools' computed-value panel is the right instrument here. The specified panel shows what you wrote; the computed panel shows what the browser actually resolved and passed down. When they disagree, inheritance or the cascade made a decision you did not expect — and now you have the model to find out which one.

The family tree metaphor holds further than it might seem. Traits pass from parent to child in a defined way, earlier resolutions lock in before they travel, and an outside rule — even a minor one — can override what the family line would have passed along. The browser is just very precise about the order it checks.
